# CLAUDE.md

Guidance for Claude Code (or any AI coding assistant) working in this repository. For the full architecture/history writeup, see `Claude-Reference-Session-Summary-V11.3.md` (owner-only package) if it's present alongside the code — that document is the long-form version of everything summarized here, and is renamed to match the current version on every release.

## What this is

Net-monit: a self-hosted, on-prem network/infrastructure monitoring tool. Flask backend, server-rendered Jinja2 + vanilla JS frontend (no build step, no framework), SQLite + YAML for storage. Single customer per installation, no multi-tenancy, no cloud backend.

## Running it locally

```bash
pip install -r requirements.txt --break-system-packages   # or use a venv
python3 app.py
```
Serves on port 50113 by default (`NETMON_PORT` env var to override). No `.env` auto-loading — see `.env.example` for supported environment variables and how to actually supply them to the process.

## Before making changes

1. **Grep before you build.** This codebase has a documented history of the same feature getting implemented two or three times across different sessions, with the old attempt never deleted (see the dashboard-layout/view-mode dead-code cleanup in the V8.2 changelog). Before adding a new per-user preference, a new device config field, or anything that smells like "storage for X", search for whether X already half-exists somewhere first.
2. **Read the relevant checker before touching the alert pipeline.** `monitor/alerts.py::evaluate_device()` (thresholds -> state) and `process_alerts()` (state -> email decision + escalation) are the most bug-prone files in this codebase historically. Trace the full call chain (scheduler -> evaluate_device -> process_alerts -> email_notifier / db.log_alert / db.upsert_active_alert) before changing any of it, not just the function you're editing.
3. **Version/port/service-name convention is load-bearing — and updating it is now automatic, every release, unprompted.** If you're cutting a new release, the port number literally encodes the version (`50` + version digits, e.g. V8.6 -> 5086). Update version, port, Windows service name, Linux service name, install directories, and registry key together — **do this on every release by default, even if the person doesn't explicitly ask for it in that session's prompt; they've stated this once and it applies going forward, not just when repeated.** Do NOT blanket-rewrite every occurrence of the old version string — historical changelog comments like `# V7.2: added X feature` document when something actually shipped and must stay as-is; only rewrite strings asserting the *current* version/identity. When in doubt whether a given line is historical or current-identity, prefer checking how the same pattern was classified in the most recent `DOC-Claude-Reference-Session-Summary-V8.x.md`'s migration checklist over re-deriving it from scratch — but always re-verify against the actual file, since new stale strings get discovered on every pass (four file headers were found stuck at V3.5 during the V8.4 rename, missed by a prior pattern-only audit).
4. **Credential encryption is keyed by device method, and that's easy to get wrong.** `monitor/crypto.py`'s `CRED_FIELDS` decides which fields get Fernet-encrypted before hitting `config.yaml`. If you add a new feature that can attach `ssh`/`powershell` credentials to a device regardless of its *primary* method (like V8.2's service/task watching), make sure the encryption logic checks for those sections unconditionally, not just when they match the primary method — this was a real gap caught during V8.2 development, not a hypothetical.
5. **Never touch `flask.request` / `session` — or anything built on them (`_tok()`, `_session()`, `_email()`, `_client_local_ip()`, `_require_*`) — from a background thread.** Flask's request context is thread-local and does not follow a request into a `threading.Thread` (or an APScheduler job). Read what you need (client IP, actor email) on the request thread *before* spawning the thread and pass plain values in. V10.1 shipped a live-progress speed test that violated this ("Working outside of request context"); V10.3 fixed the call site and V10.4 made those helpers context-safe with `has_request_context()` as defence in depth — the rule still stands. Any new `threading.Thread` in `app.py` must be checked against it.

6. **Never skip a version/port number without a checked reason, and never write a justification you haven't verified.** The increment is strictly +1 unless the *next* port is actually confirmed blocked (by a check you ran, not an assumption). Mid-build during the V10.4 speed-test fix, a session jumped straight to "V10.5" with no port conflict behind it, then wrote "there was no V10.4" into the shipped Setup Guide to explain the gap — a fabricated product-history claim, caught by grepping this file and the prior reference doc for evidence before shipping and finding none. It was renamed back to V10.4 and the sentence removed before the zip went out, but re-verify: before naming ANY release, grep this file and the most recent `Claude-Reference-Session-Summary-*.md` for the target version/port; if neither shows a real reason to skip, don't.

7. **A version sweep is not one blanket find-replace — text falls into three categories, and mixing them up corrupts the docs.** Discovered the hard way: the V10.4→V10.5 sweep (for the button-rename release) ran a straightforward `10.4`→`10.5` substitution guarded only against lines containing the literal tag `V10.4:` (colon required). That missed plain prose, and broke three things at once: lesson #5 and lesson #6 *in this file* both got mangled (lesson #6 especially, since it's a narrative *about* a version mistake and mentions "V10.4" and "V10.5" many times in ways a colon-anchored regex can't tell apart — the fabricated-sentence quote, the actual correction, and the real current version all got flattened into one wrong number); and `docs/DOC-Setup-Guide.md`'s "Upgrading" section had its cumulative port/service-name/install-dir lists silently lose their V10.4/50104 entry entirely (`...→ 50103 → 50105`, skipping 50104, instead of `...→ 50103 → 50104 → 50105`) because a list *extension* was handled as a single-value *replacement*. The three categories, and the rule for each:
   - **Current-identity strings** (version in a header/title, the default port, an install path shown as "here's where it goes") — blanket-replace old→new every release. This is the only category the simple regex approach is actually safe for.
   - **Historical narrative** (anything describing a specific past event: what a specific past version fixed, quoted fabricated text, what a correction actually did) — never touch the version number in these at all, regardless of what tag or punctuation surrounds them. A "VX.Y:" colon prefix is a *hint* something is historical, not the definition of it; prose without a colon is just as historical. When in doubt, read the sentence — is it stating what's true *now*, or narrating something that happened *then*?
   - **Cumulative enumeration lists** (the port chain, the service-name chain, the "your old install directory might be one of these" list, the firewall-ports list) — never replace an entry in these; *append* the new one and leave every old entry exactly as it was. A `10.4`→`10.5` regex run across one of these silently deletes history instead of extending it, and the damage is easy to miss because the line still looks well-formed.
   Fix applied retroactively (see the `Claude-Reference-Session-Summary-V10_6.md`, if present, for exactly what was corrected). Going forward: after any sweep, `diff` the touched `.md` files against the previous release's copy line-by-line and manually classify every changed line into one of these three buckets before shipping — grepping for a keyword guess (e.g. "does this line mention 'context' or 'fix'") is not enough, as lesson #6 itself proved by being missed that way.

   **This is not just a `.md`-file problem, and remembering a file list is not enough — it recurred in the very next sweep, one file over.** The V10.5→V10.6 sweep correctly excluded `CLAUDE.md` and `docs/DOC-Setup-Guide.md` by name (the two files just fixed above), and then did the exact same append-vs-replace damage to `monitor/checkers/network_scan.py` and `templates/networkscan.html`'s port-recognition tables instead — dropping 50105 from both while adding 50106, even though this exact pair of files had already needed the identical fix once before, during the V10.4→V10.5 release. Don't rely on a remembered list of "the risky files." After ANY sweep that touches a port number, run this check — it doesn't require knowing which files matter, it just needs the expected sequence:
   ```python
   import re
   expected = [5086, 5087, 5088, 50100, 50101, 50102, 50103, 50104, 50105, 50106, 50107]  # extend by one each release
   for path in <every tracked file>:
       ports = sorted(set(int(p) for p in re.findall(r"\b(50\d{3}|508[678])\b", open(path).read())))
       if len(ports) > 1 and ports != expected:
           print("GAP:", path, ports)
   ```
   Run it before every release from now on, not just when something already looks suspicious.

8. **Test network code against a link with a real bandwidth cap — never against an infinitely fast localhost.** V10.6 "fixed" the speed test's connection churn, passed every test, and then reported 22 % of the real speed on a 12 Mbps line and 50 % on 30 Mbps (a "5 s" test took 24 s): after the deadline each worker drained the rest of its chunk (`r.read()`), dragging the test out and dividing the bytes by the inflated time. A localhost mock delivers a whole chunk instantly, so the drain was free and the bug was invisible. Use a throttled test server (token bucket per direction, shared by all connections) for any speed-test change. Rules the V10.7 engine follows and a future change must keep: (a) the MAIN thread ends each phase at its deadline; workers never decide when to stop; (b) never finish or drain an in-flight response after the deadline; (c) other threads may only `shutdown()` a socket (that wakes a blocked read) — the owning worker closes it, because closing from outside races inside `http.client`; (d) the rate window ends AT the deadline (or at the last byte, if every connection died early), never at "whenever the threads noticed"; (e) count upload bytes when the SERVER has answered (per-stream completion events) — bytes "handed to the socket" include megabytes of kernel buffer and over-read on slow uplinks; (f) measure latency to the SAME host that carries the throughput (V10.5 and earlier pinged 1.1.1.1 while downloading from speed.cloudflare.com — different anycast prefixes, which an ISP can route to different data centres); (g) a direction that failed is `None`, never `0`.

9. **Do not build on Ookla's Speedtest CLI, or anything that shells out to it — its licence forbids what this product is.** The EULA grants "personal, non-commercial use ... on a single personal computer", and bars making the software or its functionality available "on a network where it is capable of being accessed by more than one device", and installing it on routers or other non-personal devices. Net-monit is commercial and any signed-in user's browser can start a test. Matching speedtest.net exactly means using Ookla's servers; the licence-clean routes are a commercial agreement with Ookla, or pointing the test at a nearby server the customer controls (`speedtest.targets`, LibreSpeed-compatible — built in V10.7). The `speedtest-cli` library in `requirements.txt` predates this and its standing under Ookla's terms for third-party clients was NOT verified: an open question for the owner, not something to deepen. `speedtest.engine: builtin` skips it. Why numbers can differ from speedtest.net even when nothing is broken: this product measures the route to its target (Cloudflare by default), speedtest.net measures the route to a server inside your ISP.

10. **Numbers that look like versions but are not.** `font-size:10.6px` appears 14 times in the CSS and templates; a plain `10.6`→`10.7` regex rewrites every one (earlier sweeps very likely nudged them 0.1 px per release without anyone noticing). A version regex must refuse a match preceded by a digit or dot, or followed by a digit, `px`, `em` or `%`: `(?<![\d.])10\.6(?![\d]|px|em|%)`. After every sweep count `\d+\.\dpx` before and after — the two numbers must be equal.

## Testing conventions used in this repo

There's no formal test suite (`pytest`, etc.) yet — validation has so far been done as targeted, throwaway scripts run against a temp SQLite file with a monkey-patched clock where timing matters (see the alert-timing state-machine tests from the V8.2 session for the pattern). If you're touching:
- **Database schema** — write a migration-path test: build a fake pre-change database with the *old* schema and a real data row, run the new `init_db()` against it, assert no crash and no data loss. This is the single highest-value test in this codebase, because it's the one that actually protects existing customers during an upgrade.
- **Alert timing / escalation logic** — monkey-patch `alerts.time.time` and `alerts.email_notifier.send_alert_email` so you can simulate minutes/hours passing instantly and assert on exactly which emails fired and when, rather than trying to reason about it by inspection. This caught a real bug during V8.2 development (a premature-resend issue that only manifested once time was actually simulated) that a pure code review missed.
- **Any Python file** — `python3 -m py_compile <file>` at minimum; better, actually `import` the module (catches cross-module reference errors `py_compile` can't). `app.py` is safe to import directly (guarded by `if __name__=="__main__":`) and importing it lets you inspect `app.app.url_map` to confirm routes registered as expected.
- **Any JS file** — `node --check <file>` for syntax at minimum.
- **The speed-test flow** — drive `/api/speedtest/run-async` + `/api/speedtest/status/<id>` through `app.app.test_client()` with `speedtest_check.check` faked, and call `_client_local_ip()`/`_email()`/`_finish_speedtest_result(result)` from a bare `threading.Thread` (they must not raise). The client-side `runTest()` fallback logic can be exercised in Node by extracting the function text and mocking `fetch`.

11. **Never patch `sys.stdin` / `sys.stdout` / `sys.stderr` from a library or checker module.** In V10.7 an owner edit at the top of `monitor/checkers/speedtest_check.py` replaced the process-wide streams with fake `StringIO` objects to silence `'NoneType' object has no attribute 'fileno'` (raised by the optional `speedtest-cli` library when the Windows service, which runs under `pythonw.exe`, has no console). `app.py` imports that module, so the edit changed the whole service process; the service then no longer served the dashboard (manual `python app.py` still worked, which hid the cause). V10.8 rule: (a) the ONLY place that may give a console-less process real streams is the very top of `install_service.py`, which opens `os.devnull` (real file objects with a valid `fileno()`) before any import; (b) code that needs a console (speedtest-cli) must check `_std_streams_usable()` and skip itself, never fake the streams; (c) any startup failure of the Flask thread is logged to `logs/service.log`, and `SvcDoRun` stops the service if that thread dies so the Windows recovery action restarts it. Test service-style startup by running the app with all three streams set to `None` before import (see `tests/` -- `pw_sim` style check in the V10.8 reference file). Caveat: Linux emulation passed with and without the owner edit, so the exact Windows failure was NOT reproduced here; the fix removes the cause by design rather than by reproduction.

12. **The built-in speed test is the default engine; `speedtest-cli` is opt-in (`engine: auto`).** V10.8 made the console-less guard correct but, because the service now had valid null streams, `speedtest-cli` started running and *won* the engine race: result text "Measured with speedtest-cli against <server>", no live Mbps (its API has no progress hook), so the dial stayed dead, and the server it picked was in Frankfurt for a Dubai site. The owner's own V10.7 edit had only "worked" because it made the library fail and the built-in test run. Lesson: when a fix changes which code path wins, run the user-visible flow (gauge + note), not just "does a number come back". Also: a target answering HTTP 429/503 must be backed off from (halve the streams at most once a second, honour Retry-After, retire streams, say so in the warning) -- never retry in a tight loop, which turns a rate limit into a ban and showed up as "21 connection errors". Tests: `tests/test_rate_limit.py` (note: a 429 window must cover the FIRST requests; later requests reuse open connections and never see it).

13. **Licensing is asymmetric (V11.0): the app verifies, only the generator signs.** V10.9 and earlier derived keys with `HMAC-SHA256(device_id:activation_code, SECRET)` truncated to 10 base-36 characters, and the same secret sat in `monitor/license.py` AND the generator, so anyone who could read the app could mint keys (and a 52-bit tag is brute-forceable anyway). V11.0 uses Ed25519: message `b"NETMONIT-LICENSE-V1|" + UPPER(device_id) + b"|" + UPPER(activation_code)`, 64-byte signature, written as `NM1-` + 103 Crockford-base32 characters in groups of five (127 characters with dashes, 106 without). Consequences to remember: (a) old keys are rejected on purpose -- no compatibility path, the UI says "old-format key"; (b) the key is too long to type, so the activation box is a textarea and the page only tidies, the server decides; (c) `_PUBLIC_KEY_B64` in `license.py` is changed ONLY by `LicenseKeyGenerator.py --rotate-keys --app-dir`, which also voids every issued key; (d) the generator refuses ids that are not exactly 16 hex characters (a typo must not mint a key for the wrong machine); (e) a bad/missing public key fails CLOSED; (f) the Activation Code includes the install path, so every new versioned install folder needs a new key -- pre-existing behaviour, now documented; (g) Windows PowerShell 5.1 has no Ed25519, so the old `LicenseKeyGenerator.ps1` was deleted, not ported. Do not reintroduce a shared secret "for convenience".

14. **Thresholds: one catalogue, rendered by every screen (V11.1).** Before V11.1 each of three screens (Settings > Thresholds, the Settings notify window, the Devices notify window) kept its own hard-coded list of the six DEVICE metrics, none had an entry for method `url`, so a website showed CPU/Memory/Disk, and the save loop only read those six rows -- a site's `response_ms` could never be saved from the UI. Now `monitor/threshold_meta.py` is the ONLY place that defines a metric (label, unit, group, `lower_is_worse`, min/max, recommended warning/critical, healthy text, hint) and the method -> metrics map. It feeds `alerts.DEFAULT_THRESHOLDS`, `GET /api/threshold-meta`, server-side `validate_thresholds()` and the alert wording; `static/js/threshold_ui.js` (ThrUI) renders and reads the tables for all three screens. **To add a metric: add it to `threshold_meta.py` (and make the checker output that key). Do not copy the list into JS or into a template.** Rules baked in: direction matters (`ssl_days_left` alerts when the value FALLS below the threshold, so warning must be HIGHER than critical; the flag travels inside the threshold dict so overrides keep it); precedence is notify-window > per-device > global > a site's own `url_config` fields (`max_response_ms`, `ssl_warn_days`) > catalogue defaults; every save is validated on the server (range, number, direction) and the UI shows the server's message; the table shows ONLY the metrics of the device's method and the save keeps only those rows.
15. **A function that is only called on a rare path will not be found by the happy-path tests (V11.1).** `alerts._build_short_alert_text` was called for SMS/call alerts since V8.5 and never defined, so every alert for a device with SMS or call numbers raised NameError; `setup_wizard.py` used `ex` inside a Tk callback that runs after the `except` block has deleted it. `tests/test_static_names.py` now runs pyflakes and fails on any undefined name -- keep it in `run_all.sh`. Also keep one test per OUTBOUND path (email, SMS, call) with the transport mocked.
16. **Site timing probe (V11.1).** `url_check._probe()` makes ONE extra best-effort connection per check and times DNS, TCP connect and TLS handshake separately and reads the certificate expiry. It must never raise and must never turn a reachable site into an offline one; the only effect it may have on reachability is a certificate confirmed EXPIRED (`ssl_days_left` = 0). A field it could not measure stays `None` and is not evaluated. Tests use a real local HTTP server and a local test CA (`SSL_CERT_FILE`) so the real verification path runs.
17. **Apply-to-all actions change ONLY what their label says (V11.2).** `POST /api/settings/thresholds/apply` (scope `devices`/`sites`) saves the sent metrics as the global defaults and removes the per-monitor `warning`/`critical`/`enabled` override of exactly those metrics; a per-metric `wait_sec` is a timing setting and is kept. `POST /api/settings/notify-timing/apply` (scope `all`/`devices`/`sites`) changes only `alert_trigger_mode`, `alert_notify_mode`, `notify_cooldown_sec` and (in "sustained" mode) `escalation_after_sec_l1`, and drops per-metric `wait_sec` overrides so the applied wait really wins (alerts.py reads `thresholds[metric].wait_sec` before the device's L1 delay). Both go through `app._save_notify_merged()`, which writes the whole notify row back with everything else preserved -- never call `db.set_device_notify` with a half-filled argument list (it overwrites every column, including emails and SMS/call numbers). Both validate server-side, require admin, write the audit log, and are covered end to end (including "no email before the applied wait") by `tests/test_apply_all.py`.
18. **Threshold tables are compact; details live in ONE shared floating "!" box (V11.2).** `threshold_ui.tableHTML` renders only name, unit, Enabled, Warning, Critical (and Wait). Direction, meaning, allowed range, recommended values and the healthy text come from `ThrUI.infoHTML(metric)` and are shown in a single `position:fixed` box (`#thr-pop`) appended to `<body>`, driven by document-level delegated listeners installed once by `ThrUI.bindInfo()`. It must stay a body-level fixed box: an absolutely positioned popover inside the table would be clipped by the `overflow-x:auto` wrappers and by the modal. Behaviour contract (tested in `tests/test_info_popover.js`): hover/focus shows it while the pointer is on the button or the box; click pins it and shows the X; X, Esc or clicking the button again closes it; a pinned box ignores other buttons; it flips left / moves up near screen edges; it closes if its button leaves the DOM. Settings > Monitors must show the human word ("Healthy"), never the raw status key `ok`; the dashboard map is `STATUS_LABELS`, Settings uses `STATUS_TEXT`.
19. **Publishing to GitHub: what must never be in the repository (V11.3).** The vendor private key (`license_private_key.pem`, anything `*.pem` / `*.retired`), the License Key Generator, the Claude reference summary, `.env`, `data/` contents and `FIRST-RUN-ADMIN-TOKEN.txt` are owner-only: `.gitignore` lists them and the repository is built from the *application* zip plus `site/`, `.github/` and `tests/` only. The GitHub Pages demo (`site/index.html`) is one self-contained file with simulated data; its `REPO` constant at the top of the script must be set to `user/repo` once for its links to work. CI (`.github/workflows/ci.yml`) runs `tests/run_all.sh` steps 1 2 3 9 10 11 12 13 14 15 16 17 with `PY=python`; `run_all.sh` reads `PY` from the environment and `cd`s to its own folder at the start of every step, so any subset of steps can be run from anywhere. The shipped `config.yaml` has `devices: []` -- never ship sample monitors.
20. **Releases between full builds are PATCHES (V11.3 patch 01 onward).** A patch zip (`tools/make_patch.py OLD NEW`) holds only added/changed/deleted files, each with a SHA-256 (text files hashed with CRLF folded to LF), plus `tools/apply_patch.py` (stdlib only) and wrappers. The applier refuses a wrong base version, out-of-order patch numbers, edited local files (unless `--force`), damaged files, path traversal and any protected path (`data/`, `logs/`, `config.yaml`, `*.db`, `secret.key`, `.env`, `venv/`); it backs up every file it replaces, stops/starts the service, verifies hashes, rolls back on any failure, and records `NN | name | date | summary` in `PATCHES-APPLIED.txt`, which About shows as "Patches applied". An installed service keeps its port and name (the Windows service registers `NETMON_PORT`/`NETMON_SVC_NAME` itself), so a patch never renames anything; a new port/service means a new FULL build (V11.4 / 50114). Patch names: `Net-monit-V<base>-patch-<NN>.zip`, NN incremental. `--repo` applies the same patch to a git checkout (including tests/, site/, README). Do not bump `APP_VERSION` in a patch.
21. **Every license-key entry point must accept the whole NM1 key (V11.3 patch 01).** There are two: the Activation page (also what the Admin panel links to) and Settings > License. The Settings box was still the V10 `XXXXX-XXXXX` input (`maxlength=11`, formatter cut at 10 characters) until patch 01, and its result text printed the literal `&#10003;` because `textContent` does not decode entities (use real characters or `\u2713`). Both must use a `<textarea>`, group in fives after `NM1-`, cap at 110 characters, apply the same incomplete/old-format checks, and are covered by `tests/test_license_ui.py`.
22. **Global thresholds live in `cfg["global_thresholds"]` and the alert engine must read them fresh (V11.3 patch 02).** Settings > Thresholds (Save, Apply to all devices/sites) writes `config_manager.update_global_thresholds` -> `cfg["global_thresholds"]`. Until patch 02 `scheduler._poll_device` read only the legacy `cfg["defaults"]["thresholds"]` from the job's config snapshot, so NO global value saved in Settings ever changed a live status or alert (only per-monitor Notify-window overrides did); the unit tests passed because they handed the engine the right dict themselves. Rules now: always use `config_manager.effective_global_thresholds()` (legacy `defaults.thresholds` as base, `global_thresholds` on top, read from the live config on every poll, never from a job's stale copy); layering lives in ONE place, `alerts.effective_thresholds()` (defaults < site's own Sites-page values < global < per-device config < Notify overrides), used by `evaluate_device` and by `/api/urlmonitor/results` (which returns `ssl_state` / `response_state` so the Sites table colours with the same thresholds). Any test of threshold behaviour must go through `scheduler._poll_device` with a STALE config copy (`tests/test_live_thresholds.py`), not through a hand-fed `evaluate_device` call. The Device / Website tables are shown one at a time by a Devices | Sites switch (patch 03; patch 02 had them side by side).
23. **A monitor is OFFLINE only when it is really silent -- never on one failed check, never because OUR code failed (V11.3 patch 03).** Reported symptom: many false "offline" emails (metric `availability`, value 0.0) for devices and sites that were reachable. Causes fixed: (a) `_poll_device` turned ANY single failed check into `offline` (only URL checks had one 2-second re-try), (b) an exception inside a checker was recorded as `reachable: False`, i.e. a bug or resource problem looked like a dead device, (c) `ping_check` trusted one English "% loss" sentence, so a ping in another Windows language was parsed as 100 % loss, and Windows counted "Destination host unreachable" replies as received. Rules now: every method except speedtest is re-tried `offline_retries` times (default 2) `offline_retry_delay_sec` (3) apart; OFFLINE needs `offline_confirm_polls` (2) consecutive polls that each failed every attempt; until confirmed the previous status is kept and the reason is logged (`logs/service.log`: "unreachable ... Poll k of n" / "OFFLINE confirmed ... [reason]"); a checker that raises is a monitoring error: held, logged at ERROR, and only surfaced after 5 in a row. The three numbers live in `cfg["defaults"]` (Settings > Escalation > Offline detection, `/api/settings/offline-detection`, clamped by `scheduler._OFFLINE_LIMITS`, device-level keys of the same names override). `ping_check` counts reply LINES (`TTL=` or `: ... time=/< N ms`), not translated summaries. The scheduler pool is 30 workers. Any new checker must return `{"reachable": bool, "error": "<reason>"}` for "no answer" and may raise for its own failures. Tests: `tests/test_false_offline.py` (step 15). The Thresholds tab shows ONE category at a time (Devices | Sites switch, `#thr-root[data-view]`, each category with its own Save / Apply to all / Fill buttons; `saveGlobalThresh(scope)` keeps the other category's saved values).
24. **Monitors are grouped by TYPE (what it is) and METHOD (how it is checked); thresholds, lists and the dashboard use both (V11.3 patch 04).** `threshold_meta.DEVICE_TYPES` / `TYPE_LABELS` / `METHOD_LABELS` / `scope_metrics(kind, key)` are the single source; types are free strings on the device (Switch and Router were added next to Network device, Firewall, Windows/Linux server, VMware host, NAS, ...), "shared folders" = method `disk_usage`. Threshold priority, low to high: built-in < site's own Sites-page values < All devices (`global_thresholds`) < **method** scope < **type** scope < `device["thresholds"]` < the device's Notify override -- implemented once in `alerts.effective_thresholds(device, global, notify, scoped)`; scoped values live in `cfg["scoped_thresholds"] = {"type": {...}, "method": {...}}`, read fresh each poll (`config_manager.effective_scoped_thresholds()`), edited through `POST /api/settings/thresholds/scoped` (`apply=true` also removes the group's own per-device values of the sent metrics, keeping `wait_sec`; empty thresholds clear the scope). Rows that only say `enabled: true` are dropped server-side (`_drop_noop_rows`) so "blank" always means "inherit" and "Comes from" stays truthful. `GET/POST /api/devices/<id>/thresholds` serve the dashboard device window (double-click a tile): effective values, the deciding layer (`_threshold_sources`), the device's own values; POST changes only that device's overrides for its method's metrics via `_save_notify_merged`. Lists (Settings > Monitors, Escalation, Notifications, Thresholds details) get ONE shared filter bar (`static/js/monitor_filters.js`: search, type incl. "Servers (all)" / "Network gear (all)", method) driven by the row attributes `data-mon-id/-name/-type/-method` (`MonFilter.attrs(d)`); a MutationObserver re-filters re-rendered rows, so any new device list only needs those attributes and one `MonFilter.mount(host, scope)`. Deep links: `/devices#edit=<id>` and `/devices#notify=<id>`. Tests: `tests/test_scopes.py` + `tests/test_patch04_ui.js` (step 16) use real API payloads and the real client code.
25. **A page script must never be able to starve the browser (V11.3 patch 05; patch 04 froze the Settings pages).** Cause: `MonFilter` watched a whole tab with a MutationObserver while its own "Showing X of Y" label lived INSIDE that tab; rewriting the label (even to identical text) is a DOM change, so the observer re-triggered itself from the microtask queue forever and every Settings tab (and the whole page) stopped responding. Rules: (1) never observe a subtree that contains elements the callback writes to -- ignore records whose target is inside your own widget; (2) write to the DOM only when the value really changed; (3) run re-filter work from a timer (`setTimeout`), never straight from the observer callback, and coalesce it; (4) keep a circuit breaker (more than 25 runs per second -> disconnect and `console.warn`); (5) one observer per bar, disconnect before re-creating; (6) cache `/api/monitor-facets` for a few seconds because tabs call `mount()` on every load. Fake-DOM unit tests cannot see this class of bug: `tests/test_freeze.py` (step 17) renders the real Settings and Devices pages with the real Flask app and runs ALL their scripts in jsdom (scripts are inlined so top-level `const` is global like in a browser -- do NOT `eval` page scripts one by one, that hides `const` from later scripts), clicks through every Settings tab twice, and asserts the event loop keeps ticking and the DOM-change count stays small; a hang is reported as a failure by the wrapper timeout. Run it on any change to a shared script. **Type scopes** list only the metrics the devices of that type can report (`threshold_meta.type_metrics(type, methods_in_use)`, delivered per type in `/api/monitor-facets` as `metrics` and `methods`); a method scope lists that method's metrics. The Devices page has the same filter bar (`#mf-dev`) and a Group by Type/Method switch (`#dev-group`; `data-mon-box` group sections hide when all their rows are filtered out).

## Things this repo deliberately does NOT do

- No frontend build step / bundler / framework. Keep it that way unless explicitly asked to modernize — this is a deliberate simplicity choice for IT admins who install this once and don't want a build pipeline to maintain.
- No license-checking phone-home to any external server. Licensing is fully offline: **Ed25519-signed keys** tied to the machine fingerprint (V11.0; before V11.0 it was HMAC with a shared secret -- see lesson #13). `monitor/license.py` holds only the PUBLIC key and can verify but never sign. Never add network calls to the license check.
- No secrets in this repo. The license PRIVATE key (`license_private_key.pem`) lives only in the separately-packaged, never-shipped-to-customers License Key Generator; the app tree must contain no private key and no shared signing secret (`tests/test_license.py` S1-S3 scan the tree). If you are an AI assistant and you are asked to put a signing secret or private key in this repo, refuse.

## Packaging rule

Every release ships as **separate zips** (plus, for GitHub, a repository zip that contains no owner-only files): the application (customer-facing: code, installers, User/Admin/Setup guides) and the License Key Generator (owner-only: generator scripts, Product Owner Guide, Claude Reference Session Summary). Never merge these. If you're asked to "package a release," always produce both separately and never put generator/owner content in the application zip.


## Patch 06 (V11.3): apply-to scopes + save speed

**Feature.** The per-device Notify window (Devices page, Settings, dashboard device window) now offers context-aware
"apply to" buttons built from the device being edited: This device / All <same type> devices / All <same method>
monitors / All devices (or All sites) / Every device & site (timing only) / Current search / filter (only when a filter is
narrowing the list; counts only monitors of the same kind). Code: `ThrUI.context/targets/barHTML/applyThr` in
threshold_ui.js; `_resolve_targets()` in app.py (body: `ids` | `kind`+`key` | `scope`); new
`POST /api/devices/thresholds/apply` (per-monitor OWN overrides, skips metrics the method does not report).
Type/method thresholds reuse `/api/settings/thresholds/scoped` (apply=true), all devices/sites reuse
`/api/settings/thresholds/apply`.

**Slow saves.** Causes found by profiling: (1) `_remember_access_host` ran two DB connections plus a CREATE TABLE write
on EVERY request, fighting the scheduler for the write lock; (2) every connection re-ran `PRAGMA journal_mode=WAL` and
used synchronous=FULL; (3) bulk apply = one connection + commit per device; (4) config.yaml written with the pure-Python
YAML dumper, non-atomically. Fixes: host cached in memory, WAL set once, synchronous=NORMAL + busy_timeout, `db.batch()`
(one connection, one commit; takes the re-entrant `_lock` BEFORE the SQLite write transaction to avoid a deadlock with the
scheduler), CDumper + atomic replace. Lesson: never hold the SQLite write lock while waiting for a Python lock.


## Patch 07 (V11.3): dashboard custom views + the dashboard remembers where you were

**Problem.** `currentCategory` / `currentSeverity` lived only in JS variables, so every visit to the dashboard started on
"General" with no filter.
**Fix.** Every tab/severity change is saved (a) in the browser (`localStorage nm_dash_last_<email>`, instant, no flash) and
(b) on the server (`POST /api/dashboard/last-view`, per user, debounced) so it also follows you to another PC.
`restoreLastView()` runs first in DOMContentLoaded.
**Custom views.** Named tabs (max 12 per user, max 500 tiles) of the monitors you pick, stored per user
(`/api/dashboard/custom-views`, user pref `dashboard_custom_views`; cached in localStorage `nm_dash_views_<email>`).
A view shows only its tiles, hidden tiles included, worst first (critical, offline, warning, unknown, ok) when "priority
order" is on (default), re-sorted on every 5 s poll. The tab carries a dot with the worst state inside it. Editor modal
`#cv-overlay`; tile right-click gets "Add to a custom view..." and (inside a view) "Remove from this view". Drag / resize / hide
(Edit layout) only works on the built-in tabs.
**Lesson.** A saved custom tab can be restored BEFORE the views are loaded (fresh browser). Never treat "view not found" as
"view deleted" until `_cvLoaded` is true, or the restore silently resets to General.


## Patch 08 (V11.3): "apply to ..." really applies; real cause of slow saves; Save / Save & close / Cancel

**Why "apply to all firewalls" looked like it did nothing.** "Same type / same method / all" used to save a hidden type
default and REMOVE the devices' own values. The engine did use it, but every other firewall's window still showed the old
grey built-in numbers (the Devices-page and Settings notify windows never displayed inherited values). Now every target
(this device, same type, same method, all devices/sites, current search/filter) is written with ONE endpoint
`POST /api/devices/thresholds/apply {ids | kind+key | scope, thresholds}` as each monitor's OWN value (visible everywhere),
and blank boxes show the real inherited value + where it comes from (`inherited` in `GET /api/devices/<id>/thresholds`,
`ThrUI.inheritInfo`). "Every device & site" removed; options now: This device only / All <type> devices / All <method>
monitors / All devices (or All sites) / Current search / filter.

**Slow saves, real causes.** (1) Settings notify window: after every save it reloaded FOUR tables, each making one request per
device (the Notifications table one after another): 70+ round trips on 24 monitors. Now ONE bulk request
(`GET /api/devices/notify-all`, `db.get_all_device_notify`) and only the visible table reloads; "Save & close" closes at once.
(2) `reload_scheduler` removed and re-added EVERY job with next_run_time=now, so saving ONE device polled ALL devices at once
(SSH/PowerShell/SNMP/URL). Now jobs keep their schedule, get fresh settings, and only the saved/new device polls now.
(3) Each poll wrote every metric with its own connection+commit; now one `db.batch()` per poll (SMTP stays outside it).
Lesson: when a save "feels slow", count the requests the page makes after it, not just the save call.

**Buttons.** Notify windows (Devices, Settings), dashboard device window and custom-view editor: Save (stay open) /
Save & close / Cancel (close, nothing saved). Escalation tab: All devices / All sites / Current search / filter.
